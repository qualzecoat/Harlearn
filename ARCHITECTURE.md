# Harlearn — Architecture (slice 1)

## System layout

```
Browser (Tailscale device)
  │  http://<TAILSCALE_IP>:8100   (web only; never 0.0.0.0)
  ▼
apps/web (Next.js, standalone)
  │  same-origin /api/*  →  rewrite  →  http://api:8000/api/*
  ▼
apps/api (FastAPI, internal only — no published port)
  │
  ▼
PostgreSQL 16 (internal only — no published port)
```

Why the rewrite: the API must stay internal, and the browser cannot
reach a compose service name. The web service is the only published
surface, and it proxies API calls server-side. CORS therefore only ever
sees the web origin (`WEB_ORIGIN`), never `*`.

## Auth (locked): single-password gate

- No `users` table in slice 1. One app password, Argon2 hash from
  `HARLEARN_APP_PASSWORD_HASH` (generated by `tools/hash_password.py`,
  which never stores the password).
- On login the API creates a server-side `sessions` row and sets an
  HttpOnly, SameSite=Lax cookie holding a random token; the DB stores
  only the token's SHA-256 hash. Expiry: 7 days.
- Logout requires the per-session CSRF token and deletes the session
  row. Replaying the old cookie after logout returns 401 (tested).
- `COOKIE_SECURE` defaults to `false` because the Tailscale path is
  plain HTTP inside an encrypted WireGuard tunnel; set it to `true`
  only if the web UI is served over HTTPS.
- Password rotation: change the hash in `.env` and restart, or (planned)
  change it from inside the app into the `settings` table. The latter
  is not implemented in slice 1.

## Data-model principles (locked, for future phases)

1. **`owner_id` default `'solo'` on every future table.** Slice 1 has no
   users, but graphs, runs, experiments, connections, tasks, and scores
   must all carry `owner_id` from their first migration, so a later
   multi-user migration does not rewrite experiment history.
2. **Snapshot runs, never live references.** A Run must point at a
   frozen graph version (content hash + full node/edge snapshot), not
   at the live graph. Editing the canvas after a run must never change
   what that run means. The same rule applies to profiles: a run
   references a profile version, not the editable profile.
3. **Node graph is a DAG in the data model from day one**, even though
   the first canvas UI will only encourage linear assembly
   (fragments → assembler → model → validator). The executor must
   topological-sort; the UI must reject cycles and port-type mismatches.
   The assembler's input ports have a fixed semantic order
   (stable → context → volatile) — canvas position alone must never
   silently reorder the prompt.
4. **Per-node execution records.** A run stores, per node: input,
   output, tokens, latency, and error (or `skipped` for disabled nodes).
   The final assembled prompt is stored in full — it is the primary
   learning artefact.

## Planned but NOT implemented in slice 1

- **LLMClient provider abstraction** — a normalised interface
  (`chat(messages, params) -> {text, usage, latency, raw}`) with an
  OpenAI-compatible adapter first. No provider code exists in slice 1;
  do not describe Harlearn as able to call a model yet.
- Provider connections (Fernet-encrypted API keys, masked display,
  `/models` fetch, connection test).
- Node canvas, graphs, runs, experiments, comparisons, benchmarks,
  tools/MCP, custom nodes.

## Known slice-1 gaps and limitations

- **Login rate limiting is in-memory per process** (5 / 15 min / IP).
  With one API replica this is fine; with more replicas it is not
  shared. Move it to the database (or Redis) before scaling.
- **Alembic 0001 was verified on SQLite only in the build environment**
  (no Docker, no PostgreSQL available there). The migration file is
  written for PostgreSQL (generic types, no PG-specific features), but
  `alembic upgrade head` against a real empty PostgreSQL database
  MUST be run before the first deploy, and again on Sirius.
- **Docker images were not built in the build environment** (no Docker
  daemon there). `docker compose config` / `up --build` must be run on
  the deploy host before claiming the deployment works.
- The frontend middleware redirect is UX only: it checks for the
  presence of a cookie name. The API is the security boundary — it
  validates the session and revocation on every call, and the
  dashboard page re-checks `/api/auth/me`.
- Next.js 14 was pinned to 14.2.35 after npm warned that 14.2.18 has a
  known security vulnerability. Re-check for a newer patch at deploy time.
